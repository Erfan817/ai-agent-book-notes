# 第 2 章 学习笔记：上下文工程

> 核心一句话：上下文决定能力上限：KV Cache、提示工程、Agent Skills、上下文压缩

## 正文要点和思考

### 1. 总观点：上下文决定能力上限

上下文工程这一章先立了一个大的观点：上下文决定 Agent 的能力上限，我在前一篇笔记也提到了动态上下文。

我很喜欢书中的一个比喻：AI Agent 就是一个超级无敌厉害的员工，但你不给他一本员工手册，他不知道从哪开始干活，不知道需要从哪里了解一些信息，也不知道他的工作流程到底是什么。

### 2. Agent 如何调用大模型：API 与消息角色

那我们先了解一下 Agent 到底是怎么调用大模型的。

**先解释一下什么是 API？**

API 就是软件之间沟通的“接口和规则”，让一个程序可以调用另一个程序提供的能力，而不需要知道内部怎么实现。

API 的上下文结构就是：一次 API 请求中，系统需要携带哪些“背景信息”，让对方知道你要做什么、你是谁、之前发生了什么。

书中的观点：大模型 API 的核心就是一个**消息列表**，每一条消息都有一个标记角色（role），大模型就看这些标记来理解每条消息的含义和来源。有哪些标记呢？

1. **system**：系统提示词，由开发者编写。模型将其视为最高优先级的指令。
2. **user**：用户信息，来自终端用户的输入，也就是我们给它的信息。这是 Agent 最需要响应、也是我们最需要的一条信息。
3. **assistant**：助手信息，即模型之前的回复，包括以前调用工具的记录。
4. **tool**：工具结果。Agent 框架执行工具之后，将结果以 tool 角色的消息返回给模型，它就知道我们之前用过了哪些工具。

### 3. 简单的 API 调用流程

```text
用户
 ↓
Agent
 ↓  (API 请求)
大模型（GPT / Claude / Gemini）
 ↓  (返回结果)
Agent
 ↓
执行工具
 ↓
完成任务
```

### 4. 带工具的 Agent 多轮交互：Agent 核心循环

循环，也就是现在主流 Agent 做的 Agent Loop（智能体循环）：

```text
1. 接收目标
2. 构建 Context
   ↓
3. 调用 LLM API
   ↓
4. 得到下一步行动
5. 判断：
   是回答？  →  返回用户
   是行动？  →  调工具
6. 工具结果加入 Context
7. 回到第 2 步
```

### 5. 从 API 视角看上下文的构成

从比较大的 API 视角看一下，这个上下文到底由什么组成。

前面是**静态前缀**：每一轮上下文里它都在，优先级最高、也最稳定，包括 system prompt（系统提示词）和 tool definitions（工具定义）。后面是用户提供的对话历史和那些轨迹，会随着我们不断的互动而不断增长。

### 6. KV Cache 是什么

这里遇到第一个技术名词：KV Cache。

要理解 KV Cache 需要一点点前置知识。

**第一个前置知识：自回归生成。** 大模型是一个 token 一个 token 地生成一句话，专业名称就叫自回归生成。

**第二个前置知识：Transformer 中的 Attention（注意力机制）。** 简单来说，当前生成一个词的时候，要参考前面所有词的信息，可以简单理解为每一个 token 都和其他 token 建立关系。Attention 概念中有 3 个东西是必须要知道的：

- **Q（Query）**：我现在要找什么信息
- **K（Key）**：我有着什么信息标签
- **V（Value）**：我具体的信息内容

每一个 token 都有这三个向量。

**没有 KV Cache 会怎么样？** 演示一下：假设要生成“我喜欢吃苹果”这句话。在生成“苹果”之前，模型已经计算了“我喜欢吃”；接着生成下一步时，模型又重新计算了一遍“我喜欢吃苹果”。问题是，之前的 token 信息我们已经算过了，但每次都会重新计算一遍。

KV Cache 的思想就是把已经计算过的 Key 和 Value 保存下来，下次直接拿过来用，不用再重新算一遍。为什么叫 KV Cache？因为它缓存的就是 Key 和 Value。

**一句话总结：KV Cache 就是在大模型生成文本时，把已经计算过的注意力信息保存起来，避免重复计算，从而大幅提高生成速度。**

### 7. Chat Template

那我们给 API 的信息，模型是怎么理解的呢？这就要引入一个概念叫 Chat Template。

Chat Template 就是把“人类聊天格式”翻译成“大模型能理解的输入格式”的一套规则。每个模型的 Chat Template 可能都不一样，它是连接“人类对话”和“大模型输入格式”的转换层，把 system / user / assistant / tool 等角色信息整理成模型训练时熟悉的 token 序列。

### 8. KV Cache 和 Prompt Cache 的区别

- **KV Cache**：发生在模型推理内部，缓存的是 K 和 V 的矩阵，为了加快生成速度，作用于单次请求内的生成过程。
- **Prompt Cache**：API 和系统层面的缓存，缓存的是 Prompt 前缀的计算结果，为了减少重复计算。它可以跨请求存在，主要是为了控制整个成本和交互的延迟。

### 9. 缓存作为架构约束

这一小节说了 4 件事：

1. **提示词的排列由缓存来决定**：系统提示词和工具定义等不会变的内容，一定要放到最前面；会变的内容（比如时间），要放到最后面。
2. **子 Agent 跟父 Agent 的前缀必须一字不差**：不然子 Agent 有可能从头开始推理，相当于花两份钱干一份活。
3. **替换字符串一旦定下来，就一定要给它冻上**。
4. **改前缀的风险**：改前缀有可能不只是花两份钱干一份活，还有可能丢失整个推理过程。所以说，有新内容只在后面追加，别改旧内容。

### 10. 从缓存机制转到上下文内容的设计

上下文内容的设计，按我的理解可以分成三个部分：

1. 提示工程、提示注入和动态提示词（也就是 Agent Skills）
2. Agent 的状态栏
3. 上下文的压缩策略

### 11. 第一部分：提示工程（Prompt Engineering）

提示工程最核心的就是系统提示词（system prompt）——API 消息列表中那条 `role: "system"` 的消息。它是 Agent 的“员工手册”，定义了 Agent 的身份、行为规则、约束条件和工作流程。一个精心设计的系统提示词，能让模型在具体任务中充分发挥其通用能力。

**检验标准**：这本员工手册，如果人看完之后不知道怎么干活，那模型也不知道要怎么干活。几个维度讨论如何优化系统提示词：

- **简洁**：System prompt 必须要写得简洁。
- **格式**：人写 system prompt 时用 Markdown 标题管层次；模型对 XML 标签的语义有很好的理解，可以更准确地理解这一块到底讲了什么。Markdown 配合 XML 的双层结构，人和模型都可以舒服地看懂。
- **组织形式：流程驱动**。一步一步来，像流水一样，而不是原封不动地一股脑塞进去。人干活怎么舒服，模型也是同理。
- **业务规则**：模糊规则人应该先提前写清楚，不然大模型有可能陷入反复思考，得不到我们想要的结果。
- **Few-shot 示例**：如果对输出格式要求极严、比较难说清、比较抽象的场景，可以 few-shot 给它一个例子，让它学习一下。
- **工具定义也是提示词的一部分**。提示词的前缀只放工具名，完整说明按需追加到末尾，这样就不会破坏缓存。
- **最后也是最重要的一点：安全**。提示注入是这一切的大天敌。要把确定性逻辑外置给代码（Harness 校验），不要指望靠在 System Prompt 里连写三个感叹号“绝对禁止输出 XXX”就能 100% 拦住模型。凡是能用代码、正则、Schema 校验或工具门控拦截的硬规则，直接放到模型外围的 Harness 层做确定性拦截，给 System Prompt 减负。

### 12. 动态提示词与 Agent Skills

系统提示词不能百分之百覆盖所有场景，为了解决这个问题，Agent Skill 这个概念就产生了。

Agent Skill 就是将 Agent 能力模块化，做成独立的、可以按需加载的知识包。Skills 采用了一个叫“渐进式披露”的设计哲学：先给 Agent 看一份目录，然后再按需加载，这样既不浪费 token，也避免注意力稀释。

**Skill 要包含什么？**

Skill 要包含一个 SKILL.md 文件。头部的元数据就是给大模型的轻量级路由索引，由于元数据是判断 Agent 会不会用这个 skill 的关键，所以一定要写好“何时使用”和“何时不使用”的边界。

当 Agent 判断某个任务需要特定 skill 的时候，才加载完整的 SKILL.md 文件。调用方式有两种：

1. 用户显式调用（如斜杠命令）；
2. Agent 读完元数据目录之后，自己判断需要这个 skill，再调用专用的 skill 工具。

### 13. 怎么写好一个好用的 Skill

我觉得一个合格的 Skill 应该说清楚 4 件事：**什么时候触发、按什么顺序行动、什么时候停下来确认、什么结果算完成**。这才是一个 Skill 完整的骨架——我们要把人类隐形的经验，写成模型能稳定执行的 SOP。

**骨架 4 件事（我的理解）：**

1. **触发和排除边界（什么时候用、什么时候不用）**

   除了在头部的元数据 description 里写清楚触发条件，正文也要写一句锚点，说明适用的范围和分离边界，避免模型过度匹配，出现“大炮打蚊子”的情况。

2. **分阶段动作和前置检查（按什么顺序做这件事）**

   模型最容易犯的错就是拿到任务直接开干，比如没有看目录结构就直接开始瞎写文件。所以正文不要写大段的散文。

3. **显式设立“刹车点”（哪些情况必须停下来确认）**

   模型一般有那种默认强烈的、想一次把事情全做完的倾向。如果不写死停止条件，遇到异常它可能自己瞎猜或者硬凑。刹车点要写清这三类：

   - **信息缺失和需求歧义**：比如目标不明确、关键参数缺失，要求先让模型向用户提问，禁止自己脑补。
   - **高危和不可逆操作**：比如删除数据、覆盖现有文件、外部请求或者修改核心配置，必须设置刹车点确认。
   - **连续失败熔断**：同一个报错修了 3 遍还没过，就先停下来汇报一下，别在原地一直循环，那全浪费 token 了。

4. **可验证的完成标准（DoD）**

   交互结果在什么情况下才算完成？DoD 尽量不要写“确保代码质量良好”这种特别主观的话，要给模型一个可以自我检查的客观环境和闭环判据。比如：用某一个脚本执行一下，测试通过就直接返回结果；测试没有通过，就继续修复。

**补充：Skill 的迭代**

写完 Skill 不是一劳永逸。Skill 也不是越多越好，要根据模型的表现和工作流 SOP 持续优化。

**内容 4 部分（书中的说法）：**

1. **角色与读者**：说明这个 Skill 是服务谁的，面向什么任务，输出要达到什么标准。
2. **核心原则**：只留 3 到 5 条最重要的判断，并为关键原则配上正例和反例。
3. **禁止清单**：记录高频错误、越权动作、容易误解的表达，同时写清合法的例外。
4. **参考资料**：可以放数据表、模板、范文、更详细的子文档等。

规则要尽量写成“作用域 + 动作 + 例外 + 验证方式”这个模式，避免把所有情况都堆成一张越来越长的禁用词表。

### 14. Skill 在上下文中的位置

Skill 一般不会固定地放在上下文中的某个位置，而是分成两部分（前文说的目录索引 + 完整正文），按 3 级渐进加载。这样做就是为了节省上下文窗口，并保住前缀的缓存。

- **第 1 级：元数据目录**。常见做法是放在静态指令区（system prompt 尾部）。放在前面可以让每轮对话都命中前缀缓存。
- **第 2 级：SKILL.md 正文**。模型读到目录、判断需要时才触发，完整的指令正文动态追加到对话历史的末尾——框架把它作为一个 tool result 或注入消息，插在当前对话的最后。
- **第 3 级：附属文档与脚本**。更详细的子文档按需深入阅读，Python 脚本等按需调用。

厂商对 Skill 文件的使用策略不太一样：

**Anthropic：“纯工具化” + “子上下文隔离”**

1. **纯工具化**：Anthropic 把 Skill 彻底封装在一个叫 skill 的伪工具里，把所有可用 Skill 的 name 和 description 直接拼在这个工具的描述字段里。模型需要时就发送一个 tool use 请求，系统把 SKILL.md 当成 tool result 塞回对话流里面。
2. **子上下文隔离**：Claude Code 还多做了一步。如果某个 Skill 特别重，中间要读大量文件，可以在头部声明 fork，触发时直接拉起一个独立子 Agent 上下文去跑，跑完之后再把结论传回主对话，避免上下文污染。

**Cursor：多路触发路由**

如果完全靠模型自觉——纯靠模型看 description 自己决定调不调——有时候可能会漏掉。因此 Cursor 的 Rules/Skills 机制提供了 4 种注入策略：

1. **Always**：直接焊死在最前面的 System Prompt，适合全局红线场景。
2. **Auto Attached**：按文件后缀、路径匹配，不等模型调用工具，直接在当前轮次的 user message 附近自动拼接对应规则。
3. **Agent Requested**：把 description 放在前面让模型看到，由模型按需读取。
4. **Manual**：用户打斜杠命令或者 @，强行塞进当前轮次。

**CLI 系：极简派（OpenCode、Codex 等）**

这类框架没有专用的 Skill 工具，而是复用原生的读文件工具。具体机制如下：

1. 启动时直接扫一遍本地的技能目录；
2. 把技能名、一句话简介以及 SKILL.md 的绝对路径写成一段普通文本，塞进模型的系统提示词里；
3. 需要的时候，直接调用最基础的 read_file 工具去读那个路径；
4. 读出来的内容自然就作为工具返回，落在整个对话的末尾。

这种做法对模型的原生能力要求比较高，但对框架来说，是最干净、通用性最强的一个策略。

### 15. Agent 状态栏

可以把 Agent 状态栏理解为：在整个框架上下文最末尾动态地加上一个实时仪表盘。

**为什么需要状态栏？**

Agent 在跑长任务时，比如某工具调了几次、现在改到项目的哪个目录了、原本的 TODO 完成哪几项，这些信息会十分分散地埋藏在十几轮的对话历史里。注意力机制擅长的是检索单件事实，并不擅长在单次 forward 里扫描全部历史去算统计结果。随着上下文越来越长，模型就会陷入死循环，出现遗忘约束和目标偏移。

**状态栏的做法**

由外部框架把分散在历史轨迹里的隐式状态，直接提炼为显式的、高密度的键值结构，并把文本塞到上下文最末尾。上下文最末尾也是注意力权重最高的位置，让模型不用自己去数，直接照着读就行了。

**状态栏应该放哪些信息？**

1. **Todo 清单**：标明哪些是待办、哪些是进行中、哪些是已完成，防止模型钻进局部的 bug 而偏离主线目标。
2. **当前状态**：比如当前的工作目录、Git 分支、工具的调用次数、预算消耗等。
3. **事件与感知信息**：当前系统的时间、距离上一轮操作耗费的物理时间等模型自己无法感知的外部事件。
4. **可用能力清单**：比如 Skill 的元数据列表——简单的名称和触发条件。

**怎么注入上下文？**

这是个极其关键的 KV Cache 设计。绝对不能动态修改最开头的 System Prompt——前面说过，System Prompt 一改，整个 KV Cache 前缀就全部失效了。主流实现是在 API 消息列表最末尾，由框架以 user 角色的消息注入。

**更新策略的两种权衡**

1. **每轮替换**：发新请求时，把上一轮状态栏删掉，只在末尾放最新的一条。优点是省 token、上下文干净；缺点是删掉历史中间的信息，会破坏那段之后的 KV Cache。适合短会话。
2. **持久追加**：这是 Claude Code 采用的方式。旧的状态栏消息作为历史留在原地不动，每轮只在末尾追加最新状态。虽然多用点 token，但做到了严格的“只追加不修改”，能百分之百命中前缀 KV Cache。特别适合长轨迹任务。

**落地要遵守三点**

1. 状态栏必须用确定的代码（比如正则、计数器、系统探针）去维护，绝不能让模型去批量总结。让模型生成状态栏，总结本来就是会算错的；一旦写进状态栏，主模型会无条件选择相信，然后就是错上加错。
2. 采用紧凑的结构化键值格式，不要写散文，减少模型的解析开销。
3. 光给状态读数不够，还要给与之匹配的操作策略。比如光在状态栏打印“某工具连续失败 3 次”或者“已耗时 50 秒”，模型往往不知道要怎么做。必须成对地加上提示的约束，比如“连续失败 3 次，禁止原样重试，必须切换排查方案”，读数才会真正转化为自适应行为。

### 16. 上下文压缩策略

**为什么要压缩？**

1. **解决长度约束和成本约束**：整个上下文窗口是有限的，这不单是长度问题，也是成本问题。
2. **提升思考质量**：总结后的知识比原始形式更利于模型使用。
3. **缓解模型的上下文焦虑**：当模型认为上下文即将耗尽时，可能没有完成任务就提前收尾了。

压缩的主要设计原则：与其指望模型从冗长的原始上下文中自动归纳学习，不如直接从外部主动、显式地把信息提炼成结构化的结论，再喂给模型。

**压缩与 KV Cache：看似矛盾，实则互补**

关键在于压缩发生的时机和位置：压缩不是在单次 API 调用过程中修改上下文，而是在两次 API 调用之间，由 Agent 框架对消息列表做一次预处理。这中间：

1. System prompt 和 tool definitions 永远不动——这是静态前缀，KV Cache 会持续缓存。
2. 压缩对象是对话历史中的 tool results。当框架用压缩后的摘要替换原始工具输出时，替换点之前的缓存仍然有效。

这是一个有意识的权衡：KV Cache 负责降低单步增量推理的计算成本，上下文压缩负责定期清理噪音、控制总序列长度并维持模型的注意力质量。只要做到按阈值低频触发、不动静态头部，两者就是互补的关系。

### 17. 生产级 Agent 的分层压缩机制

压缩机制我跟书中内容有一点点差异，但本质还是类似的。生产级 Agent（如 Cursor、Manus、Claude Code 之类的），不会把上下文填满后做一次全量摘要当成唯一的压缩手段，而是按成本、可逆性和对 KV Cache 的影响，拆成从轻到重的 4 层漏斗。

**第一层：入库前的拦截和落盘**

最前置的一层，发生在工具返回结果还没有塞进消息队列的那一刻。核心逻辑是“可逆卸载”，零模型成本，且不破坏 KV Cache。

- (a) 处理机制：比如跑测试跑出了 5 万行的日志，或者读了一段超大文件，框架层会直接拦截，把完整原文写进本地临时文件，上下文里只放头尾各 10 行，加上文件路径和行号索引。
- (b) 还原机制：当模型真正需要看信息时，自己会调用 grep 或分段读取工具去磁盘拿。
- (c) 核心目的：从源头防止垃圾大文本污染上下文。

**第二层：旧工具输出收缩和观测值折叠**

随着推理步数增加，十几轮之前看过的网页文档全文或命令输出，实际上已经用完了。在还没有触发大模型摘要之前，先把超过 N 轮之前的重型 tool result 原地替换成简短的占位符（例如：“已读取 xxx.ts 第 1~200 行内容，已折叠，如需查看请再次读取”）。但保证保留当时的助手思考和工具调用参数——只丢掉最占地方的原材料，不丢推理链路。

**第三层：子 Agent 的上下文隔离（天然压缩能力）**

遇到全仓库搜索某一个调用链，或者连续 10 篇文档对比这种注定会产生大量中间废料的检索性任务，主 Agent 不亲自干，而是派下一个独立上下文的子 Agent 去跑。子 Agent 在自己的沙盒里先消耗掉几万个 token 的搜索和试错过程，最后把几百字的最终结论返回给主 Agent 的上下文，然后直接销毁。这本质上就是用架构隔离代替主 Agent 的事后压缩，主 Agent 的 KV Cache 纹丝不动。

**第四层：阈值触发后的结构性摘要（Compaction，重度兜底）**

当上面三层都拦不住，上下文达到窗口的 70% 或 80% 时，触发真正的 LLM 摘要压缩：

1. **锁定关键上下文**：锁死头部的 system prompt、工具定义、项目规则文档，以及尾部的最后几轮对话和刚读过的关键代码，只把中间的历史打包压缩。
2. **强制结构化提取**：不用开放式总结，而是用固定的 schema 强制提取结构化状态，包括：用户核心目标、已完成的文件修改清单、踩过且已排除的死胡同、当前卡点与下一步计划。
3. **插入固定前缀**：将压缩生成的摘要作为新的固定前缀，插在头部后面，开启下一轮高缓存命中的周期。

**总结：生产级分层压缩的核心原则**

1. 先规则截断，再架构隔离，最后才动用大模型摘要。
2. 优先做可逆的外部落盘（例如前面提过的给路径让模型按需重读），最后才做不可逆的有损概括。

## 思考题

### 思考题 1 ★★★

> 实验 2-3 发现，滑动窗口对话历史会导致 Agent 反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏 KV Cache 前缀。

**我的回答**：历史消息一旦进入上下文就彻底只读（Append-Only），把大体积信息拦截在进入主上下文之前，外置到文件系统或子进程里，趁着缓存自然过期的窗口做无痛压缩。

### 思考题 2 ★★

> Qwen3 的 Chat Template 思维链保留机制只保留“最后一个真实用户消息之后”的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 reasoning_content——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？

**我的回答**：

1. **分层处理旧思考**：借鉴分层压缩的机制。
2. **结论状态化**：把思考里值得保留的结论，显式化成一种状态块。
3. **隔离工具调用**：隔离上百轮工具调用本身就是个危险信号。可以把中间步骤分割成若干块，分给子 Agent。
4. **守住缓存纪律**：system prompt 和工具定义这种前缀永远不动。

### 思考题 3 ★★

> 上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，这种极端的压缩是否存在“不可逆信息损失”的风险？如何解决？

**我的回答**：从 148K 压到 2K 属于有损压缩，百分之百存在细节丢失风险。可以的话，我们不做真正物理删除，只做上下文卸载，把摘要变成带索引的目录。

### 思考题 4 ★★

> Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了 bug），Agent 可能基于错误的信息做出有害的决策。这种“元信息可靠性”问题如何缓解？

**我的回答**：不要为了监督一个状态，再加一层监督 Agent 或监督工具，这样会掉进“谁来监督监督者”的套娃循环里，这是不行的。

如果是缓解状态栏污染，可以把真正的“硬事实”跟“软总结”彻底分开：

- **硬状态**：由 harness 代码进行纯确定性计算。能用代码精确算出来的状态，严禁 LLM 手写或自己思考，也不给 LLM 修改的权限。
- 软状态与真实环境冲突时，以工具的真实输出（output）作为唯一事实源；也可以在每次更新状态栏时挂一个轻量级 hook，做一次一致性校验。

### 思考题 5 ★★

> 提示工程消融实验表明，信息组织的混乱导致成功率下降 30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的“熵增”？

**我的回答**：把 system prompt 当成代码来管理，像软件工程一样拆分成“常驻内核 + 按需加载”。能用代码和 Schema 下沉实现的规则，绝不写进 prompt。把 system prompt 放进版本管理仓库：可管理、有历史，按全量 / 渐进 / 特化分层维护。

### 思考题 6 ★★★

> 本章提出“上下文学习本质上是检索而非推理”。如果这个论断成立，当前所有基于“把更多信息塞进上下文”的优化方向都需要重新审视。你认为应该如何突破这一局限？

**我的回答**：上下文的用法是检索，所以突破方向不是塞入信息的量，而是怎么改变信息的供给方式：把结论计算好之后喂给模型，而不是让模型自己去计算；把推理外包给外部工具，LLM 只干检索和编排；让噪声不进上下文，做好隔离和按需加载——整体上在管理信息密度。

### 思考题 7 ★★★

> Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发 Skill 的加载。这个“元认知”问题如何解决？

**我的回答**：

1. **把元数据当作路由条件来写**：description 采用“路由条件”而非“功能介绍”的写法，明确“何时使用 / 何时不使用”，并附典型反例，抑制宽泛匹配造成的误触发；Skill 正文加载后再设锚点。
2. **把触发判断从模型身上部分挪走**：确定性触发优先于模型自觉，设置不依赖模型自我认知的触发路径。
3. **提供可发现性兜底**：元数据目录常驻上下文，Skill 规模大时提供检索入口，把“不知道自己不知道”转化为“可以主动查阅”。
4. **数据闭环迭代**：埋点统计各 Skill 的触发率、误触发率与任务成功率；对零触发（模型想不到用它）和高误触发的 Skill，用真实任务做 before/after 校准并迭代元数据。

元认知缺口无法靠“让模型更了解自己”消除，只能靠工程手段对冲，在实际开发中磨合优化。

### 思考题 8 ★★

> Skills 机制中，Agent 从 SKILL 文件中动态读取提示词之后，后续的操作能否正确遵从这些指令？不同的模型对 Skills 模式的支持有什么区别？

**我的回答**：注入方式决定角色——Skill 正文不是写进 system prompt，而是在调用位置作为一条 user 消息注入（Claude Code 的做法），或用 `<skill>` 标签标记包装（Codex）；没有专用激活工具的运行时则用文件读取工具把正文当 tool result 读进来。上下文环境也会削弱遵从（长上下文的注意力稀释、system 提示词与 Skill 的冲突）。不同模型的区别：厂商推行的 Skills 模式是模型专门训练过的，同生态表现最佳。

### 思考题 9 ★★★

> 本章强调动态信息（如系统时间戳、工具列表顺序）的变化会破坏 KV Cache 前缀命中。在一个拥有大量工具且工具集频繁变动的生产系统中，你会如何设计上下文布局来最大化缓存命中率？

**我的回答**：

```text
┌─ system prompt 固定部分 ──────────┐
├─ 工具目录（只放名称+一句话简述）    │ ← 静态前缀：跨会话全局缓存，永远不动
├─ 稳定的核心工具定义                │
├────── 缓存边界 ──────              │
├─ 用户/会话特定配置（OS、模式、偏好）│ ← 放边界之后，避免 2^N 缓存键变体
├─ 对话历史（只追加，不改写）        │
├─ 按需加载的工具 schema            │ ← 检索到才追加
└─ 动态状态（时间戳、环境信息）       │ ← 每轮追加在末尾
```

工具列表要“目录在前，细节按需”（符合渐进式披露）；动态信息全部后置；接近压缩阈值时才触发压缩；子 Agent 与父 Agent 前缀字节级对齐，共用一份缓存。核心原则：**前缀只增不改，变化永远向后追加。**
