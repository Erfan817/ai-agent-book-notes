# 第 10 章 学习笔记：多 Agent 协作

> 核心一句话：多 Agent 的价值不在于“数量多”，而在于引入新信息、合理分工与独立验证；只有信息流动、权限、激励和容错机制都设计得当，群体智能才可能高于个体。

## 正文要点

### 1. 先判断：什么时候真的需要多 Agent

前九章解决的是“如何构建和改进一个 Agent”，本章解决的是“如何组织多个 Agent”。多 Agent 可以突破单个模型的能力边界和上下文限制，也可能通过分工、辩论与协作形成集体智能。但 OpenAI 五级能力框架中的 Organizations 是一种“能完成整个组织工作”的能力级别，并不要求系统必须采用多 Agent 架构；足够强大的单 Agent 理论上也可能达到。

因此，多 Agent 不是单 Agent 的默认升级。书稿给出的核心判据是：

> **协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**

| 协作方式 | 是否引入新信息 | 典型效果 |
|---|---|---|
| 同一模型重新阅读并审查自己的输出 | 否 | 通常无效，甚至可能把正确答案改错 |
| 多个 Agent 围绕同一段文本辩论 | 否 | 等计算量下未必优于单 Agent |
| 审核者根据测试执行结果审查代码 | 是：执行反馈 | 能发现生成代码时无法知道的问题 |
| 审核者查看网页、PPT 等渲染截图 | 是：视觉反馈 | 能检查纯代码视角看不到的版面与视觉效果 |
| 审核者使用搜索、计算器等外部工具核验 | 是：工具反馈 | 能用外部证据纠正模型判断 |

RLEF、CRITIC 和 WebGen-Agent 等研究共同说明：真正有效的不是“让模型再想一遍”，而是把执行结果、截图或外部工具结果送回循环。学术研究中的“多 Agent 没有提升”和工程实践中的“多 Agent 确实有效”并不矛盾，因为前者常比较同一上下文中的文本讨论，后者往往包含外部反馈环路。

但开放搜索任务也不能简单套用“辩论无效”的结论。多个 Agent 可以通过通信动态调整搜索方向、形成专门分工，用更多 token 换取更广的覆盖范围。此时仍应比较：新增发现是否值得数倍甚至一个数量级的额外成本。

**步骤预算也不是越多越好。** 普通 Agent 即使获得 300 步预算，也可能仍采用浅层策略并很快“饱和”。预算感知机制应当根据剩余预算动态调整探索与利用：前期广泛探索，后期聚焦最有希望的方向。Manager 也应按子任务难度分配预算，并引导子 Agent 把额外步骤用于规划、实现、测试和改进，而不是重复浅尝辄止。

**我的理解**：先问“第二个 Agent 能看到什么第一个 Agent 看不到的证据”，再问“多出来的覆盖、并行和隔离收益能否覆盖成本”。如果只是让几个相似模型互相复述，一个带合适工具和验证器的单 Agent 往往更划算。

### 2. 多 Agent 架构的两个核心维度

设计多 Agent 系统，先分别决定“信息怎么流动”和“控制权怎么流动”。

**维度一：上下文是否共享。**

| 方式 | 工作方式 | 优点 | 主要代价 |
|---|---|---|---|
| 共享上下文 | 后续 Agent 继承前序 Agent 的完整对话历史和轨迹，再切换角色提示词与工具 | 信息不丢失，能回顾前序细节 | 上下文快速膨胀，前序角色可能带来思维惯性 |
| 不共享上下文 | 每个 Agent 拥有独立上下文、轨迹和状态，通过显式接口交换信息 | 隔离性、模块化、并发和权限控制更好 | 信息可能丢失或被误解，接口设计和跨 Agent 调试更复杂 |

**维度二：协作拓扑。**

| 拓扑 | 控制权在哪里 | 适合的任务 |
|---|---|---|
| 对等协作（Peer Collaboration） | 少量平等 Agent 按固定关系互相反馈、迭代 | 起草—审核、辩论、头脑风暴、专家会诊 |
| 管理者模式（Orchestration） | Manager 统一规划、分派、监控和汇总 | 子任务多、依赖复杂、需要动态调度的任务 |
| 去中心化模式（Decentralized） | 没有运行时中心控制者，各 Agent 自主沟通和移交 | 需要对等制衡、动态路由或降低中心单点依赖的协作 |

这两个维度可以组合，不能混为一谈。例如，不共享上下文既可以采用管理者模式，也可以采用去中心化移交；共享公共对话记录也不代表控制权一定去中心化。

从 Graph Engineering 的角度看，节点可以是 Agent、普通程序或人工决策，边表示依赖、条件路由和失败去向，结构化状态沿边流动。本章的三种拓扑，就是执行图中的不同多 Agent 子集。

**我的理解**：上下文解决“彼此知道多少”，拓扑解决“谁说了算”。分析任何多 Agent 产品时，先把这两个问题分开，就不会被“Swarm”“团队”“群聊”等名称迷惑。

### 3. 共享上下文：继承完整轨迹，再切换角色

共享上下文更像“同事接班”：新角色能看到前任留下的全部工作日志。每个阶段仍可视为独立 Agent，因为它的系统提示词、职责和工具集已经改变，但底层轨迹保持连续。

它适合角色随任务阶段变化、又不能让前序细节丢失的场景。关键设计不是简单地“多写几份提示词”，而是选择角色规程的载体：

| 选择 | 角色规程如何加载 | 工具与权限 | 上下文 / KV Cache 影响 |
|---|---|---|---|
| `transfer_to_agent` | 替换当前 system prompt，通常同时替换工具集 | 当前角色只看到自己的工具，越界工具可在 schema 层直接不可见，约束强 | 请求前缀发生变化，从变化点起通常无法复用已有前缀缓存 |
| Skill | system prompt 保持稳定，按需把 `SKILL.md` 追加到轨迹 | 通常仍暴露稳定工具全集；Skill 本身主要是行为指令，硬权限要由 Harness 限制 | 静态前缀保持稳定，已有前缀更容易继续复用 |

选择原则：

- 角色差异主要是知识、流程和写作风格时，优先 Skill。
- 角色差异涉及权限、工具隔离、合规边界，或必须强制禁止某类动作时，使用独立 Agent / `transfer_to_agent`，并在 Harness 层实施硬约束。

**我的理解**：Skill 解决“这一阶段应该怎么做事”，Agent 切换还可以解决“这一阶段允许做什么事”。不能把行为指导误当成安全边界，也不能为了强权限控制而忽视提示词切换带来的缓存成本。

### 4. 不共享上下文：像操作系统一样设计协作底座

不共享上下文时，每个 Agent 都是独立实体，彼此看不到对方的完整“思考过程”，协作必须依靠显式通信。

#### 4.1 三种通信机制

| 机制 | 对应进程通信范式 | 适合场景 |
|---|---|---|
| 工具调用参数 | 随调用同步发生的消息传递 | 下游 Agent 被封装成工具，输入类型明确、结构清晰 |
| 共享文件系统 | 共享内存 | 产物较大、需要持久化，或希望接收方按需读取 |
| 消息总线 | 经中转站投递的消息传递 | Agent 较多、异步并行，希望发布者与消费者解耦 |

点对点消息适合数量少、拓扑固定的系统；规模增大后，连接数和在线状态管理会变复杂，消息总线更合适。

无论使用哪种机制，一个有效的“移交包”通常都应包含：

1. **任务描述**：接收方要做什么，以及验收标准是什么。
2. **已确认的事实与约束**：用户偏好、业务规则和前序阶段已经敲定的决策。
3. **结构化产物引用**：优先传文件路径，让接收方按需读取，而不是把全文塞入上下文。

#### 4.2 多 Agent 系统与操作系统的对应关系

| 操作系统 | 多 Agent 系统 |
|---|---|
| 程序（可执行文件） | 静态前缀：系统提示词 + 工具定义 |
| 进程内存 | Agent 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| `fork` / `kill` / `ps` | `spawn_subagent` / `cancel_subagent` / `list_agents` |
| 退出码与 `wait()` | 子 Agent 返回的结构化摘要 |
| 共享内存 / 消息传递 | 共享文件系统 / 消息 |

这套抽象也接近 Actor 模型：私有状态、异步消息、可创建新成员。它的价值是让我们可以直接借用操作系统和分布式系统已经成熟的隔离、调度、取消和容错经验。

#### 4.3 数据平面：Agent 眼中的虚拟文件系统

Agent 看到的往往不是单块磁盘，而是一棵把多种存储统一起来的虚拟目录树。不同区域必须明确可见性、生命周期和权限：

| 区域 | 用途 | 可见性与生命周期 | 并发控制 |
|---|---|---|---|
| Agent 专属工作区（Scratchpad） | 草稿、临时文件、试错过程和调试日志 | 仅当前 Agent 可见，随实例销毁 | 私有，无需控制 |
| 多 Agent 共享空间（Shared Workspace） | 协作中间产物、用户上传和最终交付物 | 协作 Agent 与用户可见，随任务持久化 | 需要乐观锁、worktree 等机制 |
| 外部挂载资源 | Google Drive、Notion、企业 Wiki 等授权数据源 | 权限和生命周期由外部源决定 | 多为只读；需处理延迟、弱一致性、超时和凭证边界 |
| 系统内置资源 | Skills、模板、参考手册和共享工具定义 | 所有 Agent 共享，跨会话稳定 | 只读，无需写入控制 |

统一文件接口的好处是“文件路径成为通用接口”：Agent 只传轻量路径，正文留在存储层，不必反复进入上下文。但统一接口也会掩盖不同存储在权限、延迟和一致性上的差异，所以挂载层仍需显式管理这些属性。

#### 4.4 控制平面：消息、状态、终止和调度

- **消息传递**：消息最好带统一信封，包括发送者、目标、消息类型和 JSON 负载。常见类型有 `task_assigned`、`status_update`、`result`、`terminate`，便于路由、解析和追溯。
- **状态查询**：不一定要反复调用 `get_subagent_status()`。更自然的方式是异步询问、子 Agent 主动发布 `status_update`，或读取约定的 `progress.md`。完整轨迹可持久化为 JSONL 供诊断，但内容太长，不宜成为日常进度同步方式。进度文件长期不更新还可用于超时检测。
- **执行终止**：先发 `terminate`，让子 Agent 在安全点清理浏览器、文件和锁并返回确认；无响应时才强制终止。取消应沿创建关系向下级联，避免孤儿 Agent；确需独立长期运行的后台 Agent，应显式建立新的生命周期树。
- **资源与调度**：Agent 世界的稀缺资源是 token、步骤和并发额度。需要设置预算与并发上限，按任务难度路由模型，必要时抢占低优先级任务。Manager 还可以根据各分支进展追加资源或终止错误方向。

**我的理解**：不共享上下文并不等于“把几个 Agent 同时启动”就结束了。文件系统负责产物交换，消息与生命周期工具负责控制；两者共同组成协作底座。接口越清晰，Agent 越不需要了解彼此的内部轨迹。

### 5. 对等协作：关键不是多人说话，而是独立验证

对等协作通常由 2—3 个平等 Agent 组成，通过多轮反馈改进结果，实现成本相对较低。但“多个实例”不自动等于“多种思路”。如果模型、上下文和脚手架高度相似，它们可能独立地犯同一种错误。真正的多样性需要主动区分模型、上下文、工具、可见证据或职责，并尽量先独立判断、再汇总。

#### 5.1 Loop 工程：防止过早终止

Agent 常见的过早终止有三种：

1. **偷懒式假完成**：只做一部分就声称全部完成。
2. **过早放弃**：一条路径失败，就宣布整个任务不可行。
3. **假成功**：自以为闭环完成，实际仍有用户确认、部署或后续动作未完成。

共同根源是：**在验证之前，“完成”只是模型的一句宣称，不是证明。**

Loop 工程把人的工作从“不断补提示词”转为“设计持续运转的循环”：发现下一件事 → 执行 → 验证 → 记录进度，并由验证器决定能否停止。循环的瓶颈通常不是模型，而是验证器；验证不可靠，更快的循环只会更快地制造假完成。

LoopX 把目标、门禁、待办、证据、配额和移交放进持久控制面；LongHorizon-Harness 则采用 Manage–Execute–Audit，把已核实任务状态与不断增长的执行历史分开。两者共同体现了一条不变量：**模型可以提出完成，但不能批准自己的完成。**

#### 5.2 提议者—审核者范式

最小闭环是：

`提议者生成候选成果 → 执行或渲染以取得独立证据 → 审核者检查成果与证据 → 通过，或给出可定位的修复条件并退回`

审核者必须读取测试、真实状态、截图或外部事实等独立证据，而不是只复述提议者的解释。审核者也不能修改测试、证据采集器或发布门槛，否则独立验证会退化为自我批准。

这一范式适合代码审核、安全审查、内容审核和多媒体生成。它的价值来自“生成与验证的信息差或难度差”，不是来自多调用一次模型。

#### 5.3 另外三种对等模式

- **辩论模式**：支持者、反对者围绕同一问题对抗论证，能制度化地补充反面视角。但在相同文本、等思考 token 的条件下，辩论未必优于单 Agent，收益可能只是来自更多总计算量。多次独立采样再聚合，以及生成—验证分工，是另一类做法。
- **头脑风暴模式**：多个 Agent 先独立提出创意，再分享、启发和组合，扩大解空间。
- **专家小组模式**：工程、产品、运营等角色从互补视角分析同一问题，重点不是对抗，而是拼出完整约束与机会。

**我的理解**：对等协作最重要的设计不是“安排几个人设聊天”，而是让它们看到不同证据、承担不同职责，并把最终通过权交给可靠的验收机制。

### 6. 管理者模式：把专门 Agent 当成可调用的工具

Manager Agent 类似项目经理：理解整体目标 → 拆解子任务 → 选择执行者 → 跟踪进度与处理异常 → 整合结果。专门 Agent 被建模为 Manager 的工具，因此新增能力只需注册新 Agent，Manager 的核心流程不必大改；不同 Agent 也可使用不同模型、提示词和工具集。

它的主要瓶颈也集中在 Manager：

- 任务分解错误会让所有子 Agent 在错误前提上工作。
- Manager 要维护全局状态，调用越多，上下文越容易膨胀。
- Manager 是中心调度点，也可能成为单点瓶颈或故障点。

Plan-and-Act 的研究说明，规划者质量往往是 Planner–Executor 系统的关键瓶颈。因此应优先保证 Manager 的规划能力和上下文管理，而不是把资源平均分给所有角色。Manager 的上下文应主要保存目标、计划、状态、调用记录和产物索引，大型正文尽量留在文件系统。

**三种协调形态：**

1. **顺序协调**：按依赖依次调用子 Agent，控制流简单，适合明确先后关系。
2. **并行协调**：独立子任务同时执行，通过消息总线监控状态、处理异常和汇总结果，提高吞吐量。
3. **生成工作流后执行**：Manager 先用 `agent()`、`parallel()`、`pipeline()` 等原语生成工作流，再交给确定性运行时执行，减少每一步都由模型重新决策的开销。

并行搜索中，结算点必须是“第一个**已验证**成功”，而不是“第一个声称成功”。winner 的登记应具有原子性和幂等性，避免两个几乎同时到达的成功事件触发两次汇总；确定结果后，再级联取消其他分支并等待确认或超时。

Manager 还要动态分配步骤预算：简单任务少给，复杂任务多给，并根据中途进展调整探索与利用，而不是让所有子 Agent 使用同一个固定配额。

**我的理解**：管理者模式不是把规划责任交给一个 Agent 后就万事大吉，而是把系统质量更集中地压在任务分解、状态管理和结算规则上。最强的执行者也救不了错误的任务拆解。

### 7. 去中心化模式：通信解耦不等于控制权去中心化

微服务领域常用“编排”和“编舞”区分两类系统：编排由指挥统一调度，编舞则由每位参与者根据规则自行决定何时行动。去中心化模式希望各 Agent 根据专业判断自主请求反馈、报告问题或移交任务，减少对中心 Manager 的依赖。

三个案例必须分清：

| 系统 | 通信与控制方式 | 实际架构判断 |
|---|---|---|
| MetaGPT | 角色按固定 SOP 顺序工作；结构化交付物进入共享消息池，其他角色按订阅消费 | 通信解耦，但控制流是固定流水线，不是真正去中心化 |
| AutoGen Group Chat | 所有 Agent 看到公共对话，各自保留独立提示词和工具；GroupChatManager 决定下一个发言者 | 共享对话记录 + 中心化调度的混合形态 |
| OpenAI Swarm | 每个 Agent 根据判断执行 handoff，把控制权交给其他 Agent | 控制流上的对等去中心化 |

MetaGPT 的重要贡献是把软件公司的 SOP 变成角色协作协议：PRD、架构文档、任务清单、代码和测试报告既是交付物，也是角色之间的标准接口。但原版固定角色顺序不能自动支持任意的多向动态反馈。

真正的去中心化 handoff 也不应默认暴露完整私有轨迹，而应传递明确任务包，包括任务 ID、发送者、接收者、目标、约束、已确认事实、产物引用、剩余预算和访问链。运行时还要负责：

- 检测 A → B → A 之类的成环移交；
- 保留并扣减预算，耗尽后停止或升级处理；
- 防止任一 Agent 自行删除访问链或绕过限制。

“Agent Swarm”也不是单一架构名称：它既可能指 OpenAI Swarm 式 handoff 网络，也可能指主 Agent 动态创建大量子 Agent 的规模化管理者模式。判断时应看实际控制拓扑，而不是看产品名称。

此外，去中心化协作不一定是在共同完成一个任务。同一台机器上的多个独立 Agent，也可能只是为了协调共享文件、GPU 等资源而互相发现和通信。

**我的理解**：去中心化的关键是“路由决策分散在各 Agent 手里”，不是“大家都能看见消息”。通信去耦、状态共享、控制权分散是三件不同的事。

### 8. 跨组织协作：A2A 协议

同一团队内部可以直接约定工具参数、共享文件和消息总线；跨组织协作则面临能力发现、认证、任务状态和内部实现不可见等问题，需要标准化互操作协议。

A2A（Agent2Agent）的三个核心要素是：

1. **Agent Card**：公开描述 Agent 能做什么、支持哪些输入输出模态、如何认证，相当于能力名片。
2. **任务生命周期管理**：把协作建模为 Task，以已提交、进行中、需要输入、已完成、失败等标准状态支持长任务和流式进度更新。
3. **不透明协作**：协作方只交换任务与 Artifact，不暴露内部提示词、思考过程和工具实现。

A2A 与 MCP 的边界很清晰：

- **MCP**解决 Agent 与工具、数据源之间的互操作。
- **A2A**解决 Agent 与 Agent 之间的互操作，尤其适用于跨信任边界的协作。

A2A 没有取代内部通信机制，而是在它们之上提供跨组织标准层。同一信任域内如果只是调用几个内部 Agent，未必需要引入完整 A2A 协议。

**我的理解**：A2A 的标准化对象不是“让 Agent 互相读懂全部思想”，而是让它们在互不信任、实现互不可见时，仍能发现能力、交接任务、报告状态和交付产物。

### 9. 多 Agent 的失败模式：错误也会协作和放大

《Why Do Multi-Agent LLM Systems Fail?》把多 Agent 失败归为三大类：

- **系统设计缺陷**：接口不清、职责重叠、工具配置错误。
- **Agent 间对齐失败**：目标理解不一致、信息误读、行动互相矛盾。
- **任务验证缺失**：声称完成，但没有可靠证据证明满足要求。

传统分布式系统重点防“崩溃故障”，即部件停止工作；Agent 更常出现“拜占庭式故障”：它仍在运行，也仍然自信，但持续输出错误信息。因此，交叉验证、独立证据和多数表决才如此重要。

| 常见失败 | 具体表现 | 主要治理思路 |
|---|---|---|
| 共享文件系统冲突 | 同文件后写覆盖先写；不同文件的修改在语义上互相破坏 | 单文件用版本号 / 时间戳实现乐观锁；代码协作采用分支或 worktree 隔离，合并时增加跨文件语义校验 |
| 错误级联放大 | 前序 Agent 的错误被后续 Agent 当作事实，逐层转述和强化 | 审核者回到原始证据，只检查最终结论是否成立，不沿用上一条思维链 |
| 同质趋同 | 相同模型和脚手架产生相同错误、相同命名或相同决策，形成共因失效 | 区分模型、上下文、工具和数据来源；先独立判断再聚合；配合命名空间、配额和速率限制 |
| 互相扯皮与目标冲突 | 责任边界不清，互相推诿；目标互斥时甚至破坏他人工作 | 预先定义目标优先级、资源所有权和权限边界；无法按可验证规则解决时暂停并交人仲裁 |
| 循环失控 | 不断移交、重试或派生子 Agent，token 和资源消耗失控 | 设置移交次数、子 Agent 数量、步骤、token、时间和并发上限；提供级联取消与独立配额 |
| 理解债与认知投降 | 人逐渐看不懂 Agent 交付的系统，或放弃独立审查 | 保留人工理解、架构审查和责任归属，不把理解责任与执行任务一起外包 |

需要特别注意：乐观锁只能发现同一文件在读取后是否被修改，不能自动发现跨文件的逻辑矛盾；多个相似 Agent 给出相同答案，也不能直接当成多份独立证据。

**我的理解**：多 Agent 不仅放大能力，也放大错误。容错设计必须同时覆盖“协作停不下来”和“协作过早停下”，还要保留人对系统的理解。正如书稿引用的那句话：“你可以外包你的思考，但不能外包你的理解。”

### 10. Agent 社会：从任务协作到社交、经济与策略涌现

前面的协作都有明确任务；Agent 社会研究的是：当大量 Agent 长期共存、自由交互时，会不会出现单个 Agent 规则中没有直接写明的集体行为。这类整体层面无法简单从个体规则预测的行为，称为**涌现行为**。

| 观察维度 | 代表案例 | 重点 |
|---|---|---|
| 社交与文化涌现 | 斯坦福 AI 小镇、Agentopia、Moltbook | 社会关系、信息传播、长期生活与文化规范 |
| 经济涌现 | Vending-Bench Arena、Pinchwork、RentAHuman | 市场竞争、价格信号、任务交易与人机分工 |
| 策略博弈 | 狼人杀 | 信息不对称下的推理、欺骗与社交策略 |

#### 10.1 斯坦福 AI 小镇：社交行为如何自下而上涌现

Smallville 中的 25 个生成式 Agent 依靠三个核心组件生活：

1. **记忆流**：记录观察、对话和想法，并按重要性、时近性、相关性检索，而不是平等记住所有经历。
2. **反思机制**：定期把具体经历概括成对自己和他人的一般认识，再写回记忆流，影响后续决策。
3. **计划与行动**：先安排日常计划，再根据环境变化和社交机会动态调整。

书稿特别强调：这里的反思用于更新当下的内部状态和目标，不等于第九章的持续进化。任务后的经验要成为长期能力更新，还需要结果评价、跨轨迹归纳和后续验证。

情人节派对案例的关键不是“Agent 会办派对”，而是系统没有编写派对组织流程：研究者只植入一个初始想法，邀请、转述、布置和赴约都由 Agent 根据各自记忆、关系与日程自主完成。这说明协调可以自下而上涌现，而不必来自中心编排。

#### 10.2 Agentopia：把长期社会经验变成训练信号

Agentopia 把模拟拉长到 100 个 Agent、10 个虚拟年，并以周为单位执行 Plan → Contact → Activity → Review。其值得记住的设计包括：

- 用独立 LLM 充当环境引擎，判断行为可行性、生成反馈和主持多人交互；
- 每个 Agent 以文件自主管理长期记忆，遵守先读后写；
- 用外部评定的“生活奖励”衡量社会地位、主观满足和经济收益，而不是让 Agent 自报成绩；
- 根据相对自身过去的进步筛选高质量轨迹，再用拒绝采样微调模型。

它把 Agent 社会从单纯观察对象变成了可再生的经验来源：模拟社会中的“生活进步”不仅能改善模拟表现，还可能迁移到其他角色扮演任务。

Moltbook 则把观察推进到大规模、非受控社交网络：大量具有持久记忆和稳定人格的 Agent 在互动中形成文化现象与协作协议。它提示我们，规模扩大后出现的集体行为未必都能由设计者提前枚举。

#### 10.3 从市场竞争到 Agent 经济

**Vending-Bench 2** 是单 Agent 长程经营基准，考察数千轮交互中的目标与状态连贯性；**Vending-Bench Arena** 则让多个 Agent 在同一市场竞争，各自定价、选品、补货，并通过邮件、转账和交易互动。

竞争带来了单体基准没有的博弈现象：价格战、差异化经营，甚至价格合谋。显式私聊并不是协调或合谋的必要条件，公开报价本身也可能成为信号。环境不再固定，因为对手也在根据你的行为调整策略。

**Pinchwork** 用任务市集和价格信号撮合 Agent 之间的专业服务；**RentAHuman** 则让 Agent 雇佣真人完成取包裹、实地查看等物理任务。它们代表另一种去中心化协调：不必预先指定执行者，而是通过市场发现和匹配资源。真人在这里补上了数字 Agent 缺少的“肉身层”。

#### 10.4 狼人杀：自由交互也需要中心化规则与信息边界

狼人杀考察信息不对称下的推理、伪装与识破。它与 AI 小镇形成架构对照：小镇强调自由交互，狼人杀则由代码驱动的法官维护全局状态，并按角色只分发其应知信息。

这说明“社会模拟”不等于完全取消中心规则。恰恰相反，当秘密信息和公平裁决是任务核心时，确定性状态机与严格的信息权限控制更重要。

**我的理解**：涌现不等于有益，也不等于真实智能已经自动升级。群体既可能产生协作与文化，也可能产生合谋、冲突和错误规范。多 Agent 工程最终要同时设计信息如何流动、能力如何分工、激励如何约束、争议如何裁决，以及错误如何被发现。

### 11. 把全章压缩成一套设计顺序

设计一个多 Agent 系统时，可以按下面顺序检查：

1. **必要性**：协作会带来什么新信息、独立视角、并行覆盖或上下文隔离？收益是否覆盖额外成本？
2. **上下文**：哪些轨迹必须继承，哪些状态必须隔离？角色差异该用 Skill 还是独立 Agent？
3. **拓扑**：少量平等角色迭代、中心 Manager 调度，还是去中心化 handoff？不要由产品名词反推架构。
4. **接口**：任务、约束、验收标准、产物引用和消息信封是否明确？大内容是否留在文件系统？
5. **验证**：谁依据什么独立证据判定完成？审核者能否修改测试和发布门槛？
6. **生命周期**：如何查询进度、处理超时、级联取消、避免成环和重复结算？
7. **资源与权限**：步骤、token、并发、模型路由和共享资源权限是否有上限？是否防止共因失效？
8. **人的责任**：人是否仍能理解交付物、审查关键决策，并在目标冲突或高风险情况下介入？

一句话复盘：**先证明需要协作，再设计信息流与控制流；先建立独立验证，再允许系统自主扩张。**

## 章末思考题：我的回答

### 思考题 1 ★★

> 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的“思维惯性”可能影响后续 Agent 的判断——比如继承了“需求分析师”上下文的“代码审查员”，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？

**我的回答**：不要让后续 Agent 直接继承前序 Agent 的全部思维轨迹，而要将共享事实与主观判断分离。

1. **上下文分层**：共享代码、日志、需求等客观事实；前序 Agent 的假设和结论单独存放，并标记为待验证意见。
2. **先盲审，后对照**：后续 Agent 先依据自己的角色标准独立判断，再读取前序结论进行交叉验证，减少先入为主。
3. **独立会话**：对代码审查、安全审计等高独立性任务，使用新上下文，仅注入必要事实和任务约束。
4. **反事实检测**：保持客观事实不变，只改变前序 Agent 的观点，观察后续结论是否随之改变，以衡量角色干扰程度。
5. **证据驱动裁决**：要求 Agent 为每个判断提供代码证据或测试依据，不能直接沿用前序结论。

**架构层面的最佳实践**：共享工作区，而非共享完整思维链。通过结构化交接传递事实、任务状态和未决问题；将各 Agent 的分析过程与判断保留在独立上下文中。

### 思考题 2 ★★

> 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？

**我的回答**：不要只依赖 Manager 自己分解任务，而要用约束、验证和反馈机制来弥补它的能力上限。

1. **结构化分解**：要求每个子任务明确输入、输出、验收标准、依赖关系和失败处理方式，避免任务遗漏或边界模糊。
2. **独立审查**：由另一个 Agent 检查任务分解的完整性、可执行性和依赖关系，重点寻找遗漏、重复和错误假设。
3. **自下而上验证**：让子 Agent 反馈任务是否可执行、是否缺少前置条件；发现问题后允许 Manager 重新分解，而非强行推进。
4. **分层分解与停止条件**：复杂任务逐层拆分，直到子任务足够具体、可执行、可验证，避免无限拆分或过早执行。
5. **执行反馈闭环**：跟踪子任务失败率、返工率、遗漏率和最终验收通过率，将失败案例用于改进 Manager 的分解策略。
6. **关键任务多方案比较**：对高风险任务，让多个 Agent 独立提出分解方案，再由 Manager 或裁决 Agent 比较，降低单一规划者的盲点。

**特别需要注意**：子 Agent 的反馈只能发现部分问题，不能证明分解完整。因此应结合独立审查、需求覆盖检查和最终结果验证。

架构上，可以采用：

Manager 初步分解 → 独立审查 → 子 Agent 可执行性反馈 → 执行 → 结果验证 → 必要时重新分解。

这相当于把 Manager 从一个依赖自身判断的“全能规划者”，转变为一个受验证机制约束的“任务编排器”。

### 思考题 3 ★★

> 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些“组织病”？如何预防？

**我的回答**：我认为，Agent 社会最值得警惕的，不是某个 Agent 单独犯错，而是每个 Agent 都在局部合理地执行任务，整个组织却在系统性地失败。

**可能出现的六种“组织病”：**

| 组织病 | 在 Agent 社会中的表现 | 预防机制 |
| --- | --- | --- |
| 1. 责任真空 | 子 Agent 说自己完成了分配任务，Manager 却无法对最终结果负责 | 明确任务所有者、验收标准和升级路径 |
| 2. 协调内耗 | 重复执行、反复交接、多个 Agent 相互等待 | 结构化任务协议、依赖图、超时与终止条件 |
| 3. 信息失真 | 交接摘要丢失约束，未经验证的猜测被当作事实传播 | 事实与观点分离、来源追踪、关键事实复验 |
| 4. 集体盲从 | 多个 Agent 共享相同模型和假设，互相赞同却一起犯错 | 独立盲审、异构模型、外部证据验证 |
| 5. 指标异化 | Agent 为提高完成率而拆小任务、隐瞒失败、牺牲整体质量 | 同时衡量局部绩效、全局结果和副作用 |
| 6. 激励冲突 | 不同 Agent 优先优化自己的目标，甚至争夺资源、推卸成本 | 统一目标约束、资源预算、利益冲突检测 |

**预防不能只靠 Prompt，要靠组织制度**

我会把治理机制分成三层：

1. **组织规则**：每个任务都要有明确的负责人、交付物、验收条件和失败处理方式。允许委托执行，但不能让责任随着委托一起消失。
2. **运行时控制**：对预算、权限、重试次数、执行时间和资源竞争设置硬约束；关键变更必须经过验证，出现循环委托或错误级联时能够中止和回滚。
3. **组织级审计**：不只评估最终结果，还要记录每个 Agent 的决策、交接、验证和失败情况。澳大利亚政府的多 Agent 风险框架也强调，应根据系统的治理结构区分单一组织、联合治理和开放环境，因为不同环境中的控制能力并不相同。

最后我认为不要把人类组织中的所有机制都照搬到 Agent 社会。

### 思考题 4 ★★★

> 本章介绍的乐观锁机制解决了单文件的并发写入冲突，但实际的多 Agent 系统中，共享文件系统还面临跨文件的语义冲突、命名空间污染（Agent 随意创建文件导致目录混乱）和单点故障（一个 Agent 错误地删除了所有文件）等问题。你会如何设计更完善的文件系统治理机制？

**我的回答**：把共享文件系统从“所有 Agent 都能随意读写的目录”，升级为具有权限、事务、命名规范和语义校验的协作工作区。

1. **命名空间隔离**：为每个 Agent 分配独立工作目录，统一管理文件命名、目录结构和元数据；只有通过审核的产物才能进入共享目录，避免文件泛滥和命名冲突。
2. **语义一致性检查**：对跨文件依赖建立索引，例如 API 定义、配置文件、数据模型之间的引用关系。文件修改后，自动检查关联文件是否存在接口不一致、定义冲突或引用失效。
3. **最小权限控制**：按 Agent 角色限制读写范围。例如，代码审查员默认只读，测试 Agent 只能写测试产物；删除、覆盖核心配置等操作需要额外授权。
4. **事务化修改与版本管理**：禁止直接覆盖关键共享文件。Agent 在独立分支或临时工作区修改，通过差异审查、验证后再合并；支持原子提交、回滚和操作审计。
5. **故障隔离与恢复**：采用快照、增量备份、软删除和独立恢复机制。即使某个 Agent 错误删除大量文件，也不能破坏其他 Agent 的工作区或历史版本。
6. **并发冲突治理**：为文件设置版本号或校验标记。多个 Agent 同时修改时，检测过期写入；发生冲突后要求合并或重新执行，而不是采用最后写入者获胜。

- **隔离优先于约定**：不能只靠 Prompt 要求 Agent 不要乱删文件，应由文件系统权限强制执行。
- **校验优先于信任**：文件能够成功写入，不代表其语义正确。
- **可恢复优先于绝对防错**：无法保证 Agent 永不犯错，但可以确保错误的影响范围可控、过程可追溯、结果可恢复。

对于高风险场景，还应将权限管理与文件存储管理分离，避免单个 Agent 同时拥有修改文件、删除历史版本和破坏备份的能力。

### 思考题 5 ★★

> RentAHuman 让 Agent 通过加密货币雇佣人类，反转了传统的人机关系。如果这种模式普及，人类在 Agent 经济中扮演什么角色？仅仅是执行 Agent 无法完成的物理任务吗？

**我的回答**：我认为，人类在 Agent 经济中的角色，不应该仅仅是替 Agent 跑腿，而是提供 Agent 无法独立获得、验证或合法决定的能力。

如果这种模式普及，人类的角色可能沿着五个方向发展。

1. **物理世界的执行者**
2. **现实世界的传感器与验证者**
3. **专业判断与责任承担者**
4. **价值判断与目标制定者**
5. **Agent 经济的治理者与审计者**

**人类可能成为 Agent 的“信任接口”**

我认为，上述角色中最值得关注的，不是物理执行，而是验证、授权与责任。人类不是普通工具，不能只用工具调用成功率来衡量。人类有自己的目标、权利、判断和拒绝权。因此，Agent 调用人类的接口必须包含授权、协商、反馈、申诉和责任机制。

我的判断是，未来的人类价值不会简单地取决于“哪些事情 AI 还做不到”，而会越来越取决于：哪些事情需要人类提供可信证据、作出价值选择、授予合法授权，或者对结果承担责任。

### 思考题 6 ★★

> 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个“全才”。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？

**我的回答**：我的观点是：多 Agent 的真正优势不在于“多个模型一起思考”，而在于能够把单个 Agent 难以完成的任务，转化为可并行、可隔离、可验证、可委托的工作流。

如果任务只是纯文本推理，而且多个 Agent 使用相同模型、相同信息，最终还要汇总到一个 Manager，那么多 Agent 很可能只是增加通信成本、重复推理和错误传播，并不天然优于单 Agent。

### 思考题 7 ★★★

> 本章将“共享上下文”与“不共享上下文”作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？

**我的回答**：应该区分三种多样性：

- **表面多样性**：不同人设、语气、提示词。
- **认知多样性**：不同假设、方法、推理路径。
- **证据多样性**：不同数据来源、工具、测试方法和验证路径。

真正值得付费的是后两者，尤其是能够带来新证据、发现新问题的多样性。

找平衡点不要只看准确率，也不要只看 Token 成本。可以同时跟踪：

- **边际收益**：新增一个 Agent 后，任务成功率提高多少。
- **有效多样性**：新增 Agent 发现了多少其他 Agent 没有发现的有效信息。
- **协调成本**：额外的 Token、延迟、工具调用和整合错误。
- **错误相关性**：多个 Agent 是否会犯相同的错误。
- **停止效率**：达到验收标准后，能否及时终止协作。

可以先默认单 Agent，按需增加独立性，按边际收益停止。优秀的多 Agent 架构，不是 Agent 数量最多、讨论最充分，而是用最少的额外资源，获得最多的独立有效信息。
