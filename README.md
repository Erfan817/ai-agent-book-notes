## 第 1 章 学习笔记：AI Agent 入门



#### 什么是 AI Agent

- **定义**：一种能自主规划任务步骤、调用各种工具，并为达成目标而自我反思、不断调整策略的智能系统形态。
- **拆解公式**：

> AI Agent ≈ 认知内核 + 动态上下文 + 目标规划 + 记忆状态 + 工具行动 + 环境接口 + 反馈评估 + 安全治理 + 编排运行时

〔24〕 说明：上面这九项是**我自己整理的拆分**，不是书里的原文。书里的骨架只有两个——

> Agent = LLM + 上下文 + 工具（作者给的工程公式，**不含环境**）
> Agent = Model + Harness；Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正

下面这份对照表同理，属于我自己的记法，不要当成书上的定义去背。

如果把 AI Agent 比作一个有机体，各组件的对应关系如下：

| 组件 | 在有机体中的角色 |
| --- | --- |
| 认知内核 | 大脑 |
| 动态上下文 | 工作台 |
| 目标规划 | 前额叶 |
| 记忆状态 | 仓库 + 状态机 |
| 工具行动 | 手脚 |
| 环境接口 | 感官与世界适配器 |
| 反馈评估 | 纠错系统 |
| 安全治理 | 免疫系统 + 刹车 |
| 编排运行时 | 神经系统 + 调度中枢 |

书里那张「直觉理解 / 实现组件 / 学术概念」的对照表，补全如下（之前只抄了表头）：

| 直觉理解 | 实现组件 | 学术概念 | 含义 |
| --- | --- | --- | --- |
| 大脑 | LLM | **策略**（Policy） | 决定「下一步做什么」——面对当前信息，从所有可选行动中挑出最合适的一个 |
| 眼睛 | 上下文构造 | **观察与历史** | 把环境返回的观察与已有历史，组织成当前决策所需的信息 |
| 手脚 | 工具与适配器 | **观察/行动接口** | 规定可以读取哪些观察、发出哪些行动，以及接口用什么格式 |

注意：这三个词映射到强化学习时**不是严格一一等同**——上下文不等于整个观察空间，工具背后的对象仍属于环境。

> 重要结论：模型固定时，提升 Agent 任务表现最有效的系统工程手段，往往是重新定义或扩展**观察空间与动作空间**——也就是扩充上下文和工具。

#### 1. 认知内核（大脑）

认知内核通常由 LLM 充当。关于 LLM 以后再聊，这里先说认知内核本身：它负责理解用户目标，理解当前上下文、记忆以及工具的返回；负责推理、判断与生成，决定是直接回答、调用工具、继续规划，还是请求人类确认或终止。

目前 LLM 的主要痛点是：

- 幻觉；
- 上下文长度有限；
- 成本高；
- 延迟大；
- 不可解释性强，黑箱成分多 。

现在先进模型越来越往「模型即 Agent」的方向发展。

与其他部分的关系：它消费动态上下文，接受编排调度，调用工具、读取记忆、接收反馈，同时受安全治理约束。

#### 2. 动态上下文（工作台 / 眼睛）

书里说上下文是 Agent 的眼睛，我认同这个说法，它也可以理解为一个工作台。这里要先澄清一点：**上下文不等于记忆**——记忆是外部仓库，上下文是当前页面。

按 API 视角看，每次调用 LLM 时的上下文由**五个部分**构成 ：

- **系统提示词**（System Prompt）：由开发者写定，全程不变，相当于「岗位说明书」；里面还会带上跨会话的**用户记忆**（偏好、历史行为、背景设定）和动态注入的环境状态；
- **工具定义**（Tool Definitions）：声明可用工具的名称、功能、参数格式。**这一项我原先漏掉了，而它恰恰是最关键的一项**——没有工具定义，Agent 根本无法发起任何调用（实验 1-1 已经验证）；
- **用户消息**（User Messages）：用户输入，里面可能夹着 RAG 检索召回的**外部知识**；
- **模型回复**（Assistant Messages）：最多三部分——思考过程 `reasoning`、文本内容 `content`、工具调用请求 `tool_calls`，一次回复里三者未必同时出现；
- **工具执行结果**（Tool Results）：框架执行工具后的返回，是下一步思考的直接依据。

更精炼的记法是：**上下文 = 静态前缀 + 轨迹**。前两项（系统提示词 + 工具定义）是**静态前缀**，后三项是随交互不断增长的**动态轨迹**。这个分法很有用——后面讲 KV Cache 前缀稳定性、为什么要「只增不改」时都靠它。

我原先列的那份清单（当前目标、当前计划、记忆召回、环境观察、权限策略、输出格式约束等）算是对五部分的再展开，但不完整，**建议以后以上面这套五部分为准**。

它的难点在于上下文污染、长度限制、信息冲突、检索不相关，以及 Prompt Injection 混入。总之，**上下文质量直接决定模型的决策质量**——而且上下文残缺时的典型失败不是报错退出，而是一个看上去毫无破绽的错误答案。

定位：动态上下文是认知内核的输入接口，也是记忆、工具、环境、反馈进入决策的通道。

#### 3. 目标规划（前额叶）

ReAct 循环  是把 LLM、上下文、工具串起来的那根主线。得按书里的定义来记：它是 **Reasoning（推理）+ Acting（行动）**，实际跑起来是**三步**——先**思考**当前该做什么，再调用工具**行动**，然后**观察**工具返回的结果，带着这个结果回到思考。「想 → 做 → 看 → 想 → 做 → 看」就这么转起来，直到任务完成。

我原来把「拆解任务、排先后顺序、选子 Agent」都算进了 ReAct，其实这些是**规划层**的事 ；ReAct 这个循环本身负责的是把规划落到每一轮的判断上，并保证执行出来的东西（轨迹）能被下一轮看到。它确实像一个大管家：每一轮决定做什么、还要不要往下做——但拆任务的能力来自 LLM 的规划本领，不是循环本身。

**什么时候停**（书上给的退出条件，比我原文笼统的「判断何时终止」清楚得多）：

1. 调用了最终输出工具；
2. 模型返回了一条没有任何工具调用的响应；
3. 遇到不可恢复的错误；
4. 达到预设的最大迭代轮数。

除了 ReAct 循环，目标规划还有这些实现方式：

- **Plan-and-Execute**：先完整计划，再逐步执行；
- **DAG / 任务图**：有依赖关系的任务节点；
- **反思与重规划**：失败后修改计划；
- **路由**：决定用哪个模型、工具或流程。

它的难点是长程规划难、目标漂移、错误累积、无限循环、不知道何时停止。

与其他组件的关系：规划依赖认知内核和上下文，调用记忆和工具，接受反馈评估，并受安全治理约束。

#### 4. 记忆状态（仓库 + 状态机）

有了记忆状态，我们给 Agent 派活时它就不必从零开始，而是能复用以往学到的东西和做过的事，逐渐形成一套 skill 库。

记忆可以这样划分：

- 短期记忆：当前对话、临时草稿、工具结果；
- 长期记忆：用户偏好、历史任务、领域知识；
- 程序记忆：技能、工具用法、工作流；
- 情景记忆：过去发生过什么、当时是怎么解决的；
- 语义记忆：事实、概念、规则。

〔3〕 前两项按「时效」划分，后三项按「内容类型」划分，两套标准混在同一个列表里容易混淆，整理时可以拆成两组。

Agent 的状态则可以分成四类：任务状态（做到哪一步）、环境状态（外部世界现在什么样）、会话状态（用户是谁、说过什么）、执行状态（哪些成功、哪些失败）。

实现记忆状态主要靠：上下文窗口、向量数据库、知识图谱、关系数据库、文件系统、摘要压缩等。现在的问题往往不是「存」有多难，而是把数据「取」出来有多难，因此需要：

1. 检索相关性；
2. 合理的写入策略；
3. 防遗忘与防冲突机制；
4. 隐私隔离——记得越多，记忆污染的风险就越大。

关系：记忆为上下文提供素材，为规划提供历史经验，为反馈提供对比依据。

#### 5. 工具与行动（手脚）

书里也说，工具是 Agent 的手脚。有了工具，它才能感知外部世界、改变外部世界。我原先只按「干什么用」列了具体例子：

1. 搜索网页；
2. 执行代码；
3. 查询数据库；
4. 调用 API 读写文件（比如发邮件、建日历）；
5. 操作浏览器；
6. 控制软件或机器人。

书上其实是按「和外界互动的方向」把工具分成**五类** 〔16〕，比罗列例子更成体系，值得记住：

- **感知工具**：把外部信息取回来——搜索引擎、文件系统、API 与数据库；
- **执行工具**：真的改变世界——代码执行、文件操作、系统命令、外部 API 调用；
- **协作工具**：跟别的角色分工——委托子 Agent、请人类确认、多 Agent 协调；
- **事件触发工具**：**不是 Agent 主动调用的**，而是由外部事件（新邮件、定时任务、Webhook）反过来驱动 Agent 开工；
- **用户沟通工具**：主动把进展或提醒传给人类——消息、邮件、语音通话。

**怎么设计工具？** 书中强调要把工具描述清楚、描述简单，具体来说：

1. 参数要结构化；
2. 权限要最小化，防止它乱跑；如果是权限特别大的操作，必须先让人类过目；
3. 失败之后要可处理；
4. 调用要可审计——它是怎么调用的，整条思维链我们都要能看到；
5. 操作要尽量幂等，并配好重试、超时与回滚。

现在主要的麻烦点：

1. 怕 Agent 选错工具；
2. 怕工具参数有误，或者参数过大；
3. 怕工具带来的副作用不可逆，没有回滚手段；
4. 怕权限过大；
5. 怕用了工具之后，成本反而比单独调用 LLM 更贵。

**工具与环境接口要区分开**：

1. 工具是能力的封装 〔4〕——像一个戴着墨镜干活的人，看不透外面的世界，只会按你派的活去干；
2. 环境接口是感知与适配层——工具负责执行动作，环境接口负责把动作结果带回来。

与其他部分的关系：

1. 规划决定调用哪个工具；
2. 安全治理决定能不能调用；
3. 环境接口负责返回结果；
4. 反馈评估判断这次调用是否成功。

#### 6. 环境接口（感官 / 世界适配器）

环境接口是我们给 Agent 开的一扇窗，是它的感官，也是整个世界的适配器。它的职责是：从环境中获取信息，把行动结果转换成模型能理解的形式，让 Agent 看到自己干完活之后世界变成了什么样。

〔17〕 这里要纠一下我自己的说法：在书的框架里，**环境（Environment）并不在 Agent 边界之内**——`Agent = LLM + 上下文 + 工具` 这个公式明确不含环境，正确写法是 `Agent ↔ Environment`（两者交互，而非包含）。真正属于 Agent 的是那层**适配器**：工具的定义、调用协议、小沙箱的权限与重置机制都归 Harness；而沙箱里随行动变化的文件、外部数据库、网页、用户、物理世界，一律属于环境。所以「环境接口」这个组件，准确说是 **Harness 朝向环境的一侧**，不能把环境本身算进来。

输入包括：用户信息、网络内容、我们提供的截图和日志、API 响应、文件、传感器传来的数据等。

输出则是格式化之后的工具结果，也就是机器能理解的形式：调用工具之后的结果是什么？有没有错误信息？有没有新观察（比如找到了新的锚点或有新的发现）？并据此再更新一次状态，看调用前后有什么区别。

环境接口常见于浏览器、操作系统、数据库、文件系统、企业级软件和机器人。**如果没有环境接口，这个 Agent 就是开环的，只能凭空生成 〔5〕；有了它，才形成「观察 → 行动 → 再观察」的闭环。**

#### 7. 反馈评估（纠错系统）

完整的 Agent 工作流程是：观察 → 思考 → 行动 → 观察结果 → 评估 → 反思 → 调整 → 再行动，直到完成或停止。

评估标准从哪来？

1. 规则校验（如单元测试、数据库约束）；
2. LLM-as-a-Judge 〔6〕；
3. 人类反馈；
4. 接入外部评分器。

它每次要想的是：

1. 工具调用成功了吗？
2. 这个 plan 要不要改？
3. 整个循环有没有偏离目标？
4. 要不要停止？

现在的实践难点有两个：一是自我评估往往不可靠、不可控，没有理想中那么可信 〔7〕；二是评估之后容易无限试错、无限思考，导致成本彻底失控。

作用：反馈评估把结果送回规划、记忆和上下文，让整个 Agent 能够自我修正，不至于跑偏。

#### 8. 安全治理（免疫系统 + 刹车）

Agent 能力越大，安全治理就越重要。它主要负责：

1. **权限最小化**：不要一次性把整个环境都放开，每次尽量在沙箱里执行；
2. **人类确认**：敏感操作需要人类点头；
3. **输入输出过滤**：不能包含种族歧视、宗教敏感等内容，以及特别危险的生化类提示词；
4. **数据脱敏**与 Prompt Injection 防护；
5. **输出合规检查**，并且最好配备回滚机制 〔8〕。

书上更有用的是「护栏三层」的分法 〔20〕，它按**被绕过的难度**排序，越靠下越不依赖模型自己的判断：

| 层 | 管什么 | 例子 |
| --- | --- | --- |
| **上下文层** | 模型能看到什么 | 相关性分类器、越狱/提示注入检测、内容审核、黑名单与正则；Anthropic 的 Constitutional Classifiers 属这一层 |
| **执行层** | 模型能做什么 | 工具风险评级、独立审查进程、最小权限凭证、沙盒隔离、人在回路、PII 过滤与输出检查 |
| **数据层** | 世界最终能被改成什么样 | 数据库行级安全策略、约束与校验器、受控视图与存储过程 |

上下文层有个结构性上限：**处在同一个上下文里的 Agent，很难判断自己是否已经被注入**——所以只靠这一层给不出保证，堆叠下面的层才有意义。另外别忽略一个反向风险：**误拒绝**，为了拦住危险请求，护栏很可能把合法但形式敏感的任务一起挡掉（比如授权内的安全测试），所以评估时要两边都测。

Agent 不一定会说错话，但它有可能：

1. 删掉你 C 盘的文件；
2. 突然把邮件发给陌生人；
3. 泄露数据；
4. 调用错误的 API，产生各种副作用。

所以必须规定清楚：

1. 它能访问什么、能改什么；
2. 哪些操作必须由人类批准；
3. 出问题后能不能回滚到之前的状态；
4. 出问题之后由谁负责。

总之，安全治理约束的是 Agent 的能力——约束它的认知内核、规划、工具、行动，以及朝向环境的那层适配器。Agent 能力越来越强，安全就越不是可选项，而是必选项。将来 Agent 的研究和工作重点，很可能就在这里。

#### 9. 编排运行时（神经系统 + 调度中枢）

书中提到编排有工作流和自主规划两种方式。编排运行时负责整个 Agent 的循环，具体职责包括：

1. 状态机与任务调度；
2. 多个 Agent 之间的通信；
3. 工具注册；
4. 记忆读写；
5. 重试与超时管理；
6. 日志追踪、评估、部署与监控。

常见的编排形态：

1. 单 Agent 循环；
2. 多 Agent 协作 〔9〕：包含规划者、执行者、批评者、工具专家等角色；
3. 工作流引擎状态：就像书中演示的那样。

如果没有编排运行时，上面这些组件都只是一堆散件；有了它，才能得到一套可运行、可调试、可评估、可上线的 Agent 系统。

但这里有个平衡别走偏：**Harness 重要，不等于 Harness 越复杂越好**。Manus 官网那句话很值得抄下来——「Less structure, more intelligence.」给一个能力足够的 Agent 清晰的目标、必要的上下文和可组合的工具，程序只守住那些必须始终成立的边界；只有业务约束真的要求、或者评估反复暴露出某类稳定失败时，才把对应步骤升级成专门的验证器或确定性流程。好的结构不是替 Agent 预演全部思考，而是守住边界，把边界内的决策空间还给模型。

#### 组件怎么协同：一个例子

假设我说：「分析一下这个季度的销售数据，找出下滑原因并生成报告。」

1. **编排运行时**：接收目标，启动循环；
2. **认知内核**：理解任务；
3. **动态上下文**：组装目标与历史，确定权限和格式要求；
4. **目标规划**：把任务拆成查数据、清洗分析、画图、写报告等具体步骤；
5. **记忆状态**：检索公司的指标定义和用户偏好；
6. **工具行动**：调用数据库，使用 Python 和图表工具；
7. **环境接口**：返回查询结果和错误信息；
8. **反馈评估**：检查数据是否完整、结论是否成立；
9. **安全治理**：确认是否允许访问敏感数据，需要的话交给用户审批。

循环结束后输出报告，并记录审计日志。

#### AI Agent 与 Harness 的关系

书上给的公式很克制，先照抄下来：

> **Agent = Model + Harness**
> **Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**
> **Agent ↔ Environment**（环境与 Agent 是交互的双方，**不在公式里面**）

我自己的记法则是把它们摊开成九项：

> AI Agent ≈ 认知内核 + Harness + 环境 〔18〕
> Harness ≈ 动态上下文 + 目标规划 + 记忆状态 + 工具行动 + 环境适配器 + 反馈评估 + 安全治理 + 编排运行时 〔19〕

对照着看更清楚：认知内核就是 Model；我列的其余八项，大体能塞进书里那五项——

| 我的九维拆解 | 落到书上的 Harness 五要素 |
| --- | --- |
| 动态上下文 | 上下文管理 |
| 工具行动 + 环境适配器 | 工具接口 |
| 安全治理 | 约束 |
| 反馈评估 | 验证 + 纠正 |
| 目标规划 + 记忆状态 + 编排运行时 | 横跨上下文与工具的工程实现（书里没有单独立项） |

总结：**LLM 是大脑，Harness 是身体的神经、感官、手脚、刹车和仪表盘，而 Agent 是它们合起来在环境中的表现行为。** 顺带一提，书上用的也是「马与缰绳」的比喻——Harness 原指马具，不是限制马奔跑，而是把力气引导到正确的方向上。

### 章末习题：我的回答

**Q1（★★）** 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？

> 我还是会给它加一个更强的模型。道理很简单：同样一段工作流，65 分的模型怎么调都解不了某些任务，换个更强的一下就通顺了；而上下文和工具，本质上是可以在外部补出来的。
> 什么时候会改主意？两种情况：**一是能力相当、价格差很多**——比如 DeepSeek 配上 Claude Code 〔12〕 或其他框架，实际表现未必比那些很贵的闭源模型差；**二是瓶颈压根不在模型上**——如果失败是因为没给到该看的数据、没给到该用的操作，那换更强的模型是在花冤枉钱，这时候应该去扩展观察空间与动作空间（这才是本节的结论：钱要花在上下文和工具上）。
> 补充一条选型提醒：绝大多数 Agent 得用**支持思考（Reasoning）的模型**，只有「单步就能干完」这类极少数场景才例外。能力之外还要看**策略边界**——同一个模型在聊天产品、Coding Agent 和 API 里能被调用的能力未必一样。

**Q2（★★★）** ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？

> 先算清楚这笔账：第 i 轮要读的缓存前缀长度约与 i 成正比，累计下来是 $1+2+\\cdots+n = O(n^2)$。注意**二次增长的是累计缓存读取费用，不是轨迹长度，也不是 KV Cache 本身的大小**。
> 顺着这个思路，能做的无非几件事：①**批量压缩**——到 token 阈值时一次性压缩早期轨迹，只留结论和关键状态，千万不要每轮都压，那样既伤效果又额外赔上压缩调用和缓存重建；②**大块中间结果外置**，只留摘要，需要时再检索回来；③用**子 Agent 隔离**，让中间过程压根不进主循环上下文；④前面提过的**只增不改**，保住前缀稳定。
> 一句话概括：控制缓存的作用区域和生命周期——毕竟不是所有缓存内容都还值得留着。

**Q3（★★）**「模型即 Agent」范式意味着模型在工具调用决策上越来越自主，但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？

> 我想打个比方：汽车和发动机。现在的 F1 赛车越来越依赖空气动力学，但你不能说发动机没用了——它的发动机同样强悍；反过来，只有发动机、没有整套外壳与设计，车也跑不起来。
> 所以「模型即 Agent」是明确的发展趋势，而 Harness 就是驾驭这匹脱缰野马最好的缰绳。我们要做的是设计更好的缰绳，让这匹马把力气用在我们需要的地方。巧的是书里用的也是马比喻——Harness 原指马具，从来不是为了限制马奔跑，而是把这份力气引导到正确的方向上。
> 落到「框架未来的核心价值是什么」：决策权确实在往模型那边移，但**模型自主空间越大，出错的影响面也越大**，所以框架的价值会从「替你编排调用」转移到保障层——权限分类、**熔断器**（连续出错就自动断电）、错误恢复、**多层上下文压缩**、工具生态。以 Claude Code 为例，它 Harness 里绝大部分代码是这类保障，而不是那几个读写文件的工具本身。这有个很硬的证据：LangChain 在 Terminal Bench 2.0 上把得分从 52.8% 提到 66.5%，换的不是模型，是 Harness。

**Q4（★★）** 消融实验中「工具结果反馈」的缺失会让 Agent 反复重试直到耗尽迭代预算。生产环境中，除了工具结果缺失，还有哪些情况可能让它陷入这种循环？你会设计怎样的检测与终止机制？

> 除了工具结果缺失，我还能想到这些诱因：**工具反复报同一个错误**、**模型幻觉去调一个不存在的工具**、**上下文压缩时把关键状态压没了**、以及**任务本身压根无解**。
> 至于检测与终止：①给足**停止条件**——任务完成、没有任何工具调用的响应、不可恢复的错误、达到最大迭代轮数；②重点盯**重复调用**：对「工具名 + 参数」算个指纹，连续出现同一指纹就判定为打转；③连续失败超过阈值就升级到人工干预，或者直接上**熔断器**——像家里短路跳闸那样自动断电，别让它一直烧钱。
> 我原来举的那个例子还是成立的：用户说「给我前 1000 亿位 π」，Agent 不可能真输出一千亿位，所以得事先把这种失控框住。如果工具在执行过程中丢失 〔13〕，也应该走同一套检测。

**Q5（★）** 本章用感知、行动、策略三个维度分析了五个 Agent 产品。选一个你日常使用的 AI 产品，用这三个维度分析它，思考它的架构设计是否合理；如果由你来设计，有哪些改进空间？

> 我觉得这套维度是对的。对着书里的表头拆更清楚：**眼睛（感知）** 看到什么信息源、**手脚（动作空间）** 是开放式还是受限、能不能内部思考、**策略** 走的是什么循环。
> 我常用的个人助理是 Hermes：它会先揣测我的意图，否则很容易跑偏；行动上有时直接代理执行，有时只用 LLM 就答完了；整体策略在我看来很适合做 Personal Agent。要挑毛病的话，它的动作空间偏开放，缺少书里强调的**最小权限 + 高风险动作二次确认**。
> 要改进的话，我想加一个跨对话的控制能力——由一个「大管家」统管各个子对话。有这样的功能就更好了，说不定它其实已经有了，只是我没发现。（补一句：Anthropic 做长任务时正是这么干的——把一个任务拆成「初始化 Agent」和「执行 Agent」，让后者在每个会话里增量推进并留下清晰的交接产物。）

**Q6（★★）** 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？

> 我还真想过类似的项目。我的做法是：先用自主 Agent 把用户需求彻底问清楚，再进入工作流模式。
> 补一句更稳妥的版本：主体还是走工作流——**身份核实 → 搜索航班 → 付款 → 确认预订**四个节点，好处是「付款前不能预订」这类合规顺序由代码强制保证，不依赖模型的判断；而且就算某个节点被提示注入，攻击面也被关在那一个节点里。
> 需要灵活决策的环节（理解出行需求、临时改签、航班取消后推荐替代方案）再切回自主模式，两者在同一个系统里混着用。最后，**大额付款、退款这类高风险动作一定要加人工确认**。
> 一句话：开放的部分交给 Agent，边界和顺序交给代码。

**Q7（★★★）** 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？

> 我觉得第一步是**把评级对象从「工具」细化到「工具 + 参数」**：按可逆性、权限等级、影响面（比如是否涉及钱）算这次调用的风险等级，低风险照常放行，高风险走审查或人工确认。
> 关键在于**这个判断不能用模型来做**。一是要用**确定性的规则**——路径黑白名单、正则匹配（比如凡是命中系统目录的删除一律升级为高风险）；二是**只看结构化数据**（工具返回的 JSON 字段），不要看模型自由生成的文本，因为那部分可能已经被提示注入操纵了；三是复核必须发生在**上下文之外**，靠独立审查进程、最小权限凭证、沙箱隔离或人在回路来完成，否则它会和被注入的 Agent 一起陷进去。
> 我原来的两点依然成立：给用户弹风险提示是必需的，回滚机制也是必需的，别真的删掉了却没有后悔药。

**Q8（★★）** 本章的 Agent 产品表格中，所有 Agent 的动作空间都是「开放式」的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？

> 大概是在高合规、高风险、错误不可逆的场景里，比如自动驾驶、医疗、金融交易，或者部署在核电站的 Agent——也包括前面说的付款与退款。在这些地方，只有把动作空间限制住，它才是真正安全的。
> 书里给这类思路起了个名字，叫**防呆**（Poka-yoke，来自丰田生产体系）：像 SIM 卡的缺角让你只能顺着插、微波炉门没关好就绝不加热，**用设计消灭错误，而不是指望模型别犯晕**。受限的选项本身就是一种「约束」，天然自带这种效果。

**Q9（★★）** 人工干预机制要求 Agent 能「优雅地移交控制」。但实践中用户可能不在线、响应很慢，或者给出模糊的指令，此时 Agent 应该怎么办？

> 原则应该是 **fail-safe（故障安全）：拿不到确认就暂停，而不是默认继续执行**。这个方向和书里「所有能力默认关闭、必须显式开放」是一致的。
> 具体可以这么分工：
> 1. 高风险、不可逆的操作 → 拿不到确认就**暂停**，把待决事项写进交接文档，方便人类回来决策，也方便 Agent 之后接着做；
> 2. 低风险、可逆的部分 → 先做完，别让用户干等着；
> 3. 用异步的消息/邮件去通知用户，并设好**超时策略**——到了时间没回应，就走上面第 1、2 条的分工；
> 4. 指令含糊时，不要硬猜，先用一轮**意图澄清**把「用户说的」和「用户真正想要的」对上——书里讲 GPT-5.6 的 Deep Research 就是先问一轮需求再动手的。至于「往用户偏好方向走」，用记忆里的偏好辅助判断可以，但它不能替代确认。

**Q10（★★★）** 引言指出「好的设计原则应该穿越模型的迭代周期」，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。

> 原则我想说的是「**结构简单**」——书里引 Anthropic 的三原则也是这条打头：先做最简单的，只在被逼无奈时才加复杂度，因为每多一层抽象都会变成日后调试的新盲区。
> 具体到会过时的工程手段，我原来想到的插件化就是个好例子：现在这些 harness 都在往「一切皆插件」的方向走（书里那张框架表给 DeepSeek Harness 的定位正是这五个字），谁都能往里塞自己顺手的插件。可这类 scaffold 的宿命就是被模型吃掉——**给模型能力短板打的补丁，随着模型变强会被它自己内化**。书里的例子更直白：few-shot 示例、「让我们一步一步思考」这类提示技巧，被指令微调和推理模型内化了；输出格式修复、JSON 容错解析，被结构化输出和原生工具调用内化了；文生图那种「把大白话翻译成 SD 风格提示词」的改写节点，被模型的原生多模态能力吃掉了。
> 所以往后看，插件生态值得保留的是**能力的可发现和可组合**（渐进式披露的价值），而不是「必须先注册成某种固定形式」这件事本身——后者很可能就是最先过时的那一层。
